# ONNX Model Preparation Guide

This document explains how to prepare ONNX models and vector data for use with Re-kNN evaluation tools.

Japanese version: [onnx-preparation.ja.md](./onnx-preparation.ja.md)
English README: [README.md](../README.md)

---

## 1. Purpose of This Document

This document describes how to prepare ONNX models and input data for use with Re-kNN evaluation tools.

It is intended for users who want to:

- generate vector data from their own datasets
- evaluate Re-kNN in their own environment
- reproduce the text-domain evaluation flow
- prepare token-level or sentence-level vectors for registration

This document focuses mainly on the **Text Domain** workflow, where ONNX-based embedding generation is relevant.

---

## 2. Scope

Re-kNN currently defines the following standard evaluation targets:

- **Text Domain**: 768 dimensions  
  Target: text embeddings generated by `bert-base-multilingual-cased`
- **Pattern Domain**: 784 dimensions  
  Target: MNIST raw pixel vectors
- **Vision Domain**: 3072 dimensions  
  Target: CIFAR-10 raw pixel vectors

Among these, ONNX model preparation is mainly required for the **Text Domain**.

For MNIST and CIFAR-10 evaluation, Re-kNN uses raw pixel vectors directly and does not require ONNX model preparation.

## 3. Verified Environment

The following environment is the current reference environment for ONNX-related evaluation.

- OS: Windows 11 Professional
- Runtime: .NET 8
- Verified text model target: `bert-base-multilingual-cased`
- Intended output dimension: 768

Please note that performance and compatibility may vary depending on:

- ONNX Runtime version
- tokenizer implementation
- model export options
- pooling method
- hardware and memory conditions

## 4. Expected Workflow

The standard text-domain workflow is as follows:

1. Prepare a pretrained language model
2. Export the model to ONNX format
3. Prepare tokenizer settings
4. Convert source text into model inputs
5. Run ONNX inference
6. Extract vectors from model outputs
7. Save vectors in a format consumable by Re-kNN
8. Register vectors into Re-kNN for search and inference evaluation

---

## 5. Model Preparation Strategy

### 5.1 Recommended Model Type

For the current Text Domain evaluation, the expected vector dimension is **768**.

A suitable model should therefore satisfy at least the following:

- fixed output vector dimension of 768
- stable inference through ONNX Runtime
- reproducible preprocessing
- availability of tokenizer configuration

The current reference target is:

- `bert-base-multilingual-cased`

### 5.2 Sentence-Level vs Token-Level Vectors

There are multiple ways to extract vectors from transformer models.

Typical options include:

- **sentence-level vector**
  - e.g. pooled output
  - e.g. mean pooling over token embeddings
- **token-level vector**
  - one vector per token
  - useful when fine-grained registration is required

Re-kNN supports both search and inference workflows, but the evaluation intent matters.

For example:

- **document / sentence retrieval**
  - sentence-level or segment-level vectors may be sufficient
- **fine-grained search within documents**
  - token-level registration may be more appropriate

### 5.3 Token-Level Registration in Wikipedia JP Evaluation

In the Wikipedia JP evaluation, Re-kNN registers **all token vectors** contained in the target texts.

This means:

- the vector count does **not** represent one vector per article
- each searchable entry corresponds to a token-level vector
- the final vector count reflects token-level registration

This is why the number of vectors can be much larger than the number of source documents.

## 6. Preparing an ONNX Model

### 6.1 General Notes

Re-kNN does not require a specific export tool, as long as the resulting ONNX model:

- runs correctly in your environment
- produces reproducible vector outputs
- matches the intended dimensionality
- is paired with a compatible tokenizer pipeline

In this document, the ONNX export procedure is described using `optimum`.

### 6.2 Exporting a BERT Model to ONNX

Install the required Python modules as follows.
Please choose appropriate versions for your execution environment.

```bash
pip install transformers==4.55.4
pip install fugashi==1.5.1
pip install ipadic==1.0.0

pip install onnx
pip install onnxruntime
pip install transformers[onnx]
pip install optimum[exporters]
```

Generate the ONNX model from the command line.
In the following example, ONNX files are generated under `onnx-bert-base-multilingual-cased/`.

```bash
optimum-cli export onnx --model bert-base-multilingual-cased --task feature-extraction onnx-bert-base-multilingual-cased/
```

## 7. Preprocessing Requirements

### 7.1 Tokenization

This document does not describe tokenization in detail.
Please apply tokenization appropriately according to the BERT model you use.

The sample program implements tokenization for `bert-base-multilingual-cased`.

The maximum sequence length used in the sample program is 512.

For a concrete implementation example, please refer to the sample program included in this repository.

### 7.2 Text Encoding

Use a consistent text encoding format.

Recommended:

- UTF-8

Be careful with:

- newline normalization
- control characters
- Unicode normalization
- inconsistent whitespace handling

---

## 8. Output Vector Extraction

### 8.1 Common Extraction Methods

Depending on your use case, the final vector may be derived from:

- CLS token embedding
- mean pooling over token embeddings
- token-by-token hidden states
- a dedicated pooled output head

### 8.2 Recommended Documentation Practice

When publishing or sharing results, explicitly document:

- the ONNX model used
- tokenizer version or source
- max sequence length
- pooling strategy
- whether vectors are sentence-level or token-level

Without these details, results may be difficult to interpret fairly.

## 9. Expected Input / Output for Re-kNN

The exact format depends on your CLI or sample application, but the following conceptual structure is recommended.

### 9.1 Minimum Registration Fields

Typical registration data should include:

- `document_id`
- `sentence_id`
- token-level vectors (`float[token_count][768]`)

In the sample program, all token vectors generated from the same sentence share the same `sentence_id`.
As a result, the vector field is represented as a set of 768-dimensional vectors, one for each token in the sentence.

### 9.2 Example

Example source text:

```text
This is sample text.
Re-kNN stores both documentId and sentenceId.
```

Example conceptual data structure:

```text
document_id = 0, sentence_id = 0, token_vectors = float[tokenCount0][768]
document_id = 0, sentence_id = 1, token_vectors = float[tokenCount1][768]
```
